# anchor-mc

Paper 서버 플러그인. 엑스레이 유저를 **가짜 광석 미끼 + 위약 대조 + e-value**로 통계적으로 확정한다.
이론은 옆 저장소 `anchor`의 README/DESIGN(대안 혼합 e-value, 위약으로 p₀ 실측, 2배 안전 배수)을 그대로 따른다.
**섀도 모드 전용**: 자동 처벌 코드가 없다. 확정되면 서버 로그와 `anchor.alert` 권한자 알림만.

> **1.1단계·1.2단계(맨 아래)에서 배치 방식이 두 번 바뀌었다.** 아래 "원리"는 1.2단계 기준으로 고쳐 썼고, 이전 단계 결과·한계 중 뒤집힌 것에는 "→ 1.1절", "→ 1.2절"을 달았다.

## 원리

1. 서버가 플레이어에게 **청크 데이터 패킷을 보낼 때**(PacketEvents로 가로챔) 그 청크 안에서 (미끼, 위약) 뭉치 두 개를 (플레이어, 청크, 서버 비밀 시드)만으로 결정적으로 정한다. 뭉치는 진짜 다이아 광맥의
   모양·크기·높이를 표본으로 흉내 내고, 모든 블록이 **패킷이 담은 블록 데이터에서 여섯 면이 전부 안정적인 불투명 고체**여야 한다(→ 1.1절, 1.2절).
2. 동전 던지기로 하나는 **미끼**(그 플레이어의 청크 패킷 안 블록 데이터를 가짜 다이아 광석으로 바꿔 넣는다. 서버 월드는 그대로), 하나는 **위약**(아무것도 안 바꾸고 기록만). 같은 청크를 다시 받으면 같은 자리에 같은 미끼가 온다.
3. 플레이어(또는 캐는 블록)가 뭉치의 가장 가까운 블록 중심 반경 r 안에 들어오면 반응 1. 미끼가 화면에 있던 시간이 창(기본 240초)만큼 쌓이는 동안 안 오면 MISS로 판정하지만 미끼는 화면에 그대로 둔다.
   클라이언트가 청크를 버리면 판정 없이 노출 시간만 멈춘다(→ 1.2절).
4. 정직한 플레이어는 볼 수 없으니 둘에 같은 비율로 반응한다. 엑스레이는 미끼에만 더 반응한다.
5. p₀ = (전체 위약 반응률) × 2. 위약 관측이 100건 미만이면 p₀를 상한(0.9)에 두고, 반응 0건이면 95% 상한에 2배.
6. 계정별 대안 혼합 e-value를 **미끼 반응으로만** 누적한다. E ≥ 1/α(기본 10⁹)이면 확정.
   대안 격자를 절대 확률(0.005~0.99, 48개)로 고정하고 관측 시점의 p₀ 이하 대안은 건너뛰어서, p₀가 계속 갱신돼도 타당성이 유지된다.
7. **먼저 반응한 쪽 e-value**(1.2단계, 1.1단계의 "한쪽만 반응한 쌍" 정의를 대체): 반응이 나온 쌍마다 첫 반응이 미끼였나 위약이었나를 세는 정확 검정. 귀무에서 동전 때문에 정확히 1/2이다.
   기본 확정 규칙은 6번 혼합과 이것을 **각각 한 번이라도 문턱을 넘음**으로 묶는 것(`confirm-rule: BOTH`).

## 구조

```
src/main/java/dev/anchormc/
  core/      Bukkit을 모르는 핵심: DecoyGuard(불변식 1), DecoyEngine(패킷용 계획 prepareChunk + 메인 스레드 등록 registerChunk·회수),
             PairPlanner/Seeds/ChunkPlan/PlannedPair(결정적 계획), ResponseTracker(반응 판정, 미끼·위약 공용),
             VeinShapes/VeinProfile/VeinScanner/YBalance(광맥 모양·크기·높이 표본, 추출, 높이 보정)
  evidence/  Mixture(혼합·쌍 e-value), EvidenceEngine(계정·p₀·쌍 맞추기·먼저 반응), EvidenceStore 인터페이스 + SQLite/메모리/비동기 구현
  plugin/    Paper·PacketEvents 연동: PacketDecoyListener(청크 패킷 가로채기), PacketChunkView(패킷 블록 데이터 시야), ChunkPatcher(패킷에 쓰기),
             PacketStateTable(블록 상태 분류), PlayerRegistry, BukkitBlockView(읽기 전용), BukkitDisplay(회수 전용), 이벤트, /anchor 명령
src/sim/     서버 없는 시뮬레이터(플러그인 jar에 안 들어감). 실제 core·evidence 코드를 그대로 돌린다.
```

저장소는 `EvidenceStore` 인터페이스만 쓰므로 MySQL/Redis 구현으로 갈아 끼울 수 있다(`AnchorPlugin`의 한 줄).

미끼와 위약의 처리는 `ResponseTracker` 한 클래스가 종류를 읽지 않고 처리한다. 종류가 갈리는 곳은 `DecoyEngine`의 "보낸다/되돌린다" 두 곳뿐이다.
`PathIdentityTest`가 같은 이벤트 열(이동·채굴·이웃 변화·만료·다른 월드)을 300가지 무작위로 미끼 경로와 위약 경로에 넣어 판정·회수 기록이 완전히 같음을 확인하고,
`ResponseTracker` 소스에서 `kind` 접근이 한 줄뿐임을 검사하며, 동전이 공정하고 두 쪽 거리 분포가 같음도 확인한다.
방어 코드를 일부러 망가뜨리면(노출 알림 무시, 후보 봉인 검사 제거) 테스트가 실패하는 것을 확인했다.

e-value 타당성 테스트(`EvidenceTest`): 정직 p=p₀=0.10, 6000계정×800관측에서 P(언젠가 E≥x)가 x=5/20/100에서 각각 1/x 이하
(3σ 여유 포함), p가 p₀보다 낮거나 p₀가 관측마다 바뀌는 최악의 경우에도 성립, 위약 반응률을 실측해 쓰는 전체 파이프라인에서 정직 400계정 중 확정 비율 ≤ α.
전체 27개 테스트 통과(`./gradlew test`). 1.1단계 뒤에는 48개, 1.2단계 뒤에는 72개다(API가 바뀌어 고친 기존 테스트 포함, 각 절 참고).

## 시뮬레이터 결과 (1차 MVP 기록)

> **이 절의 표는 1.1단계에서 재현되지 않는다.** 배치가 "주기적으로 플레이어 근처 6~24블록"에서 "청크 전송 시점"으로 바뀌었고 월드도 128→256으로 키웠다.
> 결론이 뒤집힌 부분(검증형 미탐, 밀도 표, 오탐 1.5%)은 1.1절의 재측정이 대체한다. 아래는 1차 당시 기록으로 남긴다.

`./gradlew runSim --args="--runs 200 --honest 600 --minutes 120 --seed 1"` (약 80초). 실제 `DecoyEngine`/`ResponseTracker`/`EvidenceEngine`을 쓰고,
월드(128×128×80, 벌레 동굴 + 진짜 광석)·에이전트·클라이언트 표시만 가짜다. 설정은 기본값(r=3, 창 90초, 쌍 3개, 쿨다운 15초, α=10⁻⁹).
시간은 채굴 시간(이동 5틱/블록, 굴착 +9틱/블록). 정직 코호트를 먼저 돌려 p₀를 실측하고, 그 뒤 엑스레이가 같은 서버에서 계속 돈다.

**정직 오탐** (600계정, 각 최대 60분): 위약 반응 2151/73753 = 2.92% → p₀ = 0.058.

| 정직-동굴탐색 (300) | 0 | 2.0% | 1.0% | 0% | 3.85% | 3.87% |
| 정직-브랜치마이닝 (300) | 0 | 4.3% | 1.0% | 0% | 1.94% | 2.04% |

## 로컬 서버에서 직접 테스트하기

1. JDK 25 필요(Paper 26.2가 요구). `set JAVA_HOME=...jdk-25...` 후 `./gradlew build` → `build/libs/anchor-mc-0.1.0.jar`.
2. Paper 26.2 stable(build 129): `https://fill.papermc.io/v3/projects/paper/versions/26.2/builds/latest`가 알려주는 jar를 `run/`에 받는다.
   `java -jar paper-26.2-129.jar`를 한 번 돌리고 `eula.txt`를 본인이 확인해 `eula=true`로 바꾼다.
3. **PacketEvents 2.14.0 플러그인**(`packetevents-spigot`, 서버 버전에 맞는 것)을 `run/plugins/`에 먼저 넣는다(1.2단계부터 필수, `depend`). 플러그인 jar도 넣고 서버를 켠다.
   첫 기동 때 Paper가 SQLite 드라이버를 내려받고(인터넷 필요), `secret-seed`가 비어 있으면 새로 만들어 `config.yml`에 저장한다(값은 로그에 안 나온다).
4. 서바이벌 모드로 접속(크리에이티브·관전에서는 미끼를 안 넣는다). 미끼는 서버가 청크 데이터 패킷을 보낼 때 그 안에 들어가므로 Y가 -64~16인 지하로 내려가 청크 경계를 넘어 움직인다.
   미끼는 벽 속(엑스레이나 리소스팩이 아니면 안 보인다: 봉인돼 있으니까)의 다이아 광맥 모양으로, 진짜 광석과 같은 패킷에 들어 있다.
   **1.2단계의 새 동작(PacketEvents가 이 서버 버전의 청크 패킷을 읽고 다시 쓰는지, 접속 직후 청크)은 실서버에서 아직 확인하지 못했다.** 확인 순서는 1.2절.
5. 미끼 쪽으로 파 들어가 보면 이웃 블록을 깨는 순간 광석이 진짜 돌로 돌아간다(불변식 2).
6. `/anchor stats`(전체 위약 반응률 = 현재 p₀, 청크 패킷에 미끼를 넣은 횟수), `/anchor status <플레이어>`(미끼·위약 관측, 반응률, log10E, 확정 여부), `/anchor debug <플레이어>`(그 플레이어에게 계획된 미끼·위약 좌표와 상태, 1.2절). 권한 `anchor.admin`(기본 op).
   위약이 100건 쌓이기 전에는 p₀가 상한이라 확정이 안 난다.
   빠르게 보려면 `alpha: 0.01`, `min-placebo-samples: 10`으로 낮추고 미끼만 골라 파면 확정 알림이 로그에 뜬다(테스트 후 되돌릴 것).

## 한계

1. **Java 21이 아니라 25**다. "최신 안정 Paper API를 고정"하라는 조건과 Java 21이 충돌했다. 공식 문서 기준 최신 안정판은 26.2 build 129이고 그 API jar의 클래스 버전이 69(Java 25)라 21로는 컴파일이 안 된다. Java 21을 유지해야 하면 1.21.x API로 내려가야 하는데 그 경우 `api-version`과 몇몇 이벤트 시그니처를 확인해야 한다.
2. **실제 Paper 서버에서 실행해 보지 못했다.** 컴파일, jar 생성, `plugin.yml` 치환, core 27개 테스트, 시뮬레이터까지만 확인했다. Minecraft EULA는 사용자가 직접 수락해야 해서 서버를 띄우지 않았다. 이벤트 연동과 `sendBlockChange`는 위 절차로 먼저 확인해야 한다.
3. **[1.1단계에서 조건부로 뒤집힘 → 1.1절] 검증형 엑스레이는 못 잡는다.** (1차 당시) 미끼가 시야 가장자리(32블록)가 아니라 6~24블록 안에서 갑자기 뜨기 때문에, "가까이서 갑자기 나타난 광석은 무시"하는 클라이언트는 몇 번 속은 뒤 미끼를 전부 거른다(시뮬레이터 그 규칙). anchor 본편의 결론(검증형 미탐)과 같다. 미끼 등장 거리·시점을 진짜 광석 노출과 겹치게 만드는 것은 다음 층의 일이다.
4. **[1.1단계에서 재현·원인 확인·쌍 정확 검정으로 보강 → 1.1절] e-value 독립성 가정.** (1차 당시) 같은 플레이어의 여러 자리 반응은 위치가 겹쳐 상관이 있을 수 있어 "관측마다 조건부 확률 ≤ p₀"가 근사다. 정직 반응률이 계정마다 다르면(동굴 탐색 3.9% vs 브랜치 2.0%) 합친 p₀와 2배 마진에 기댄다. 밀도를 높인 실행에서 log10E ≥ 2가 이론 상한을 살짝 넘은 것이 이 징후일 수 있다. 개선안: 미끼/위약 쌍은 동전으로 정했으므로, 한쪽만 반응한 쌍의 미끼 비율이 정확히 1/2이라는 정확 검정(상관과 무관)을 e-value로 쓰는 것.
5. **시뮬레이터는 모델이다.** 월드·동굴·광석 분포, 에이전트 행동, 굴착 속도, 시야 32블록은 내가 정한 값이다. 사람 데이터가 아니고, 절대 시간(분)보다 전략 간 순위와 오탐 확인에 의미가 있다. 사람은 반응 지연·경로가 다르다.
6. **미끼가 화면에서 먼저 사라질 수 있다.** 서버가 같은 좌표의 블록 업데이트를 다시 보내면(이웃 변화 등) 클라이언트의 가짜가 진짜로 덮인다. 엔진은 활성으로 알고 있어 그 미끼의 반응은 계속 세므로 미끼 반응률이 희석된다(검출력만 손해, 오탐에는 영향 없음).
7. 이벤트 없이 월드를 바꾸는 플러그인(월드에딧 등)은 최대 0.5초(재검사 주기) 뒤에야 회수된다. 그 사이에도 미끼가 보이려면 클라이언트가 이웃이 뚫린 걸 받아야 하고, 그 패킷이 나간 직후 재검사가 회수한다.
8. 자리 뽑기는 메인 스레드에서 도는 무작위 표본(1.1단계부터 뭉치당 최대 60번×2)이다. Folia는 지원하지 않는다. 미끼 밀도와 확정 속도는 맞바꿈이라 서버에서 조정해야 한다
   (1차: 쌍 3개/15초 → 6개/5초로 신뢰100% 중앙값이 17.5분 → 9.4분. 1.1단계의 밀도표는 1.1절).
9. `shadow-mode: false`로 바꿔도 이 버전에는 처벌 동작이 없어 똑같이 로그·알림만 한다.

## 1.1단계: 검증형 엑스레이를 잡기 (청크 시점 배치, 광맥 모사, 쌍 정확 검정)

### 가설과 한 줄 결과

가설: 검증형이 미끼를 거르는 근거는 "가까이서 갑자기 나타남" 하나다. 미끼를 진짜 광석과 같은 시점(청크 전송)에, 같은 모양(광맥)으로 보내면 근거가 사라진다.

- **맞았다, 조건이 붙는다.** 미끼가 청크와 같은 틱에 도착하면 시점·모양 필터가 있어도 검증형이 잡힌다(아래 표, 밀도 E에서 검증형 3/10번: 혼합 96~100%, 기본 규칙 92~98%).
- **가설이 놓친 채널이 둘 있다.** 플러그인은 청크 데이터를 못 바꾸고 별도 블록 갱신 패킷으로만 보낸다. 그래서 (a) 미끼가 청크보다 **1틱만 늦어도**, (b) 클라이언트가 **블록 갱신 패킷으로 온 광석을 통째로 무시하면** 확정률이 0%다. **→ 1.2단계에서 미끼를 청크 데이터 패킷에 직접 넣어 닫았다(1.2절).**
- 밀도를 올리면 정직 계정에서 **혼합 e-value가 이론 한계를 크게 넘는다**(원인은 아래). **쌍 정확 e-value는 넘지 않는다.** 그래서 기본 확정 규칙을 둘 다 넘어야 하는 `BOTH`로 바꿨다.
  (→ 1.2단계에서 "쌍 정확"의 정의가 "먼저 반응한 쪽"으로 바뀌었다. 이 절의 표는 1.1 정의와 1.1 배치 기준이다.)

### 1. 청크 전송 시점 배치 (→ 1.2단계에서 청크 패킷 삽입으로 바뀜)

Paper 문서로 확인한 것: `PlayerChunkLoadEvent` "Is called when a Player receives a Chunk. Can for example be used for spawning a fake entity when the player receives a chunk."
`PlayerChunkUnloadEvent` "Is called when a Player receives a chunk unload packet. Should only be used for packet/clientside related stuff. Not intended for modifying server side."
26.2 API jar에서 두 클래스와 `Player#sendMultiBlockChange(Map<Position,BlockData>)`가 있음을 `javap`로 확인했다. **문서는 이벤트가 청크 패킷 송신 전인지 후인지 말하지 않는다**(→ 한계).

- `DecoyEngine.onChunkSent(player, cx, cz)`만 새 쌍을 만든다. `tick()`은 위치 판정만 한다(`ChunkPlacementTest`가 시간이 흘러도 미끼가 안 나감과 `spawnPair` 호출이 한 곳뿐임을 검사).
  미끼는 같은 호출 안에서 `showGuarded`로 즉시 나간다. 뭉치는 그 청크 안에만 놓는다.
- 청크 언로드: `PlayerChunkUnloadEvent` → `dropChunkFor`(복구 패킷 없이 VOID), `ChunkUnloadEvent` → 모든 플레이어의 그 청크 자리 정리. (→ 1.2단계: VOID 대신 노출 시간 정지)
- 불변식 1~4는 뭉치 단위로 유지된다: 전송 직전 모든 블록 재검사, 한 블록의 이웃이 바뀌면 뭉치째 회수(`oneExposedBlockRetractsTheWholeCluster`), 기존 무작위 이벤트 열 테스트 전부 뭉치로 통과.
- 청크 가장자리 처리: 이웃 청크가 로드 안 됐으면 "고체 아님"이라 가장자리 블록은 후보에서 빠진다.
- 부작용: 미끼가 청크 반경 근처(멀리)에 놓이므로 대부분 도달 전에 청크가 내려가 VOID로 빠진다(설정 B, 정직 6000계정: 판정 전 회수 1,591,554건 대 판정 관측 약 88,000건). 창(240초)·give-up(160)을 그래서 늘렸다.

### 2. 광맥 모사

- **표본 추출**(`VeinScanner`): 로드된 청크의 진짜 다이아 광석(일반·심층)을 26방향 연결 덩어리로 묶는다. 최소 모서리를 가진 청크에서만 한 번 센다. 이웃 청크 미로드로 잘렸을 수 있는 덩어리와 40개 초과(광맥 여러 개가 붙은 것)는 뺀다.
  600개까지 모으면 스캔을 멈춘다(`sites.profile-samples`). 표본이 40개 미만이면 바닐라 규칙 기본값(크기 4/8/12를 7 : 4 : 1/9, 높이는 위로 갈수록 줄어드는 선형 밀도)을 쓴다.
- **뽑기**: 표본 하나를 모양과 원래 높이째 뽑아 수평 대칭 8가지(y축 회전 4 × 반전 2, 두께는 유지)로 바꾸고 높이에 ±3을 더한다. 그래서 크기 분포·높이 분포·둘의 결합이 표본 그대로 재현된다.
- **위치**: 그 청크 안 균등. 모든 블록이 돌 속·봉인, 진짜 다이아 광석과 26방향으로 붙지 않음(붙으면 클라이언트에서 덩어리가 합쳐져 크기가 어긋난다), 플레이어와 6블록 이상, 같은 플레이어의 다른 자리와 가장 가까운 블록끼리 2r+2 이상.
  **위약도 같은 함수**로 뭉치 단위로 뽑는다(모양·크기·높이 함수를 같이 쓰고 동전은 그 뒤에 던진다).
- 청크 배치 후 진짜 광맥과 비교(정직 코호트, 설정 E, 진짜 6,639개 대 미끼 4,085,083개):

| 크기 | 1 | 2 | 3 | 4 | 5-6 | 7-9 | 10-12 | 13+ |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 진짜 | 7.7% | 24.1% | 17.9% | 19.8% | 18.7% | 10.4% | 1.0% | 0.4% |
| 미끼 | 9.3% | 26.0% | 18.5% | 17.8% | 17.8% | 9.2% | 1.0% | 0.4% |

총변동거리 0.041, 평균 크기 3.92 대 3.76, y 두께 1.87 대 1.84. **높이는 밀도가 높을수록 어긋난다**(표본 100계정 실행): 평균 최소 y가 진짜 −37.7일 때 미끼는 청크당 쌍 1이면 −37.1, 2이면 −36.0, 4이면 −33.9(E 1000계정 실행 −32.4).

표본은 같은 생성기에서 나온 것이라 "표본을 재현하는가"는 검증했어도 "실제 바닐라 월드와 같은가"는 검증하지 못했다.

### 3. 레드팀 강화: 검증형 엑스레이 필터

시뮬레이터의 엑스레이는 클라이언트가 아는 광석(진짜는 청크 도착 시각·경로와 함께, 미끼는 블록 갱신이 도착한 시각·경로와 함께) 중 시야 32블록 안의 가장 가까운 것으로 직진한다. 모든 필터는 클라이언트가 실제로 볼 수 있는 정보만 쓴다.

- **시점 필터**: 그 광석이 속한 청크가 로드된 뒤 0틱(허용 없음)보다 늦게 나타난 광석은 무시.
- **모양 필터**: 26방향 연결 덩어리 크기가 2 미만(단일 블록)이거나 12 초과면 무시.
- 추가한 두 가지(지시에 없음): **패킷 경로 필터**(블록 갱신 패킷으로 온 광석 무시), **전송 1틱 지연**(미끼가 청크보다 1틱 늦게 나갈 때의 시점 필터).
- 기존 전략 5종(신뢰 100/50/20%, 검증형 3/10번)은 그대로 두고 필터를 모두 켠·끈 상태로 잰다. 각 200계정, 최대 120분 채굴. 셀은 "확정률 · 확정까지 채굴 시간 중앙값".

### 4. 쌍 정확 검정

- 미끼·위약 쌍에서 미끼가 어느 쪽인지 동전으로 정했다. 두 자리 모두 판정된 쌍 중 **한쪽만 반응한 쌍**만 센다. 귀무(미끼 표시가 반응에 영향 없음)에서 "미끼 쪽만 반응"의 확률은 동전 때문에 **정확히 1/2**이고,
  p₀도 반응률의 독립성·동질성도 필요 없다. 쌍이 끝나는 시각도 동전과 무관하므로 끝난 순서로 쌓아도 타당하다(이 가정: 정직 플레이어의 행동이 미끼 표시 여부에 안 달림, VOID가 종류와 무관 — `PathIdentityTest`).
  한쪽이 VOID면 쌍째 뺀다(`voidPair`, 짝을 못 찾은 쌍은 메모리에 남지 않음을 시뮬레이터가 확인: 마지막에 0).
- e-value: 불일치 쌍마다 Bernoulli(1/2) 대 Bernoulli(q)(q ∈ (0.55, 0.999], 40개 로짓 격자)의 가능도비를 균등 혼합. `Mixture.observePaired`.
- 테스트(`PairedEvidenceTest`): 짝 맞추기 네 가지·순서 무관·VOID, 같은 쌍이 함께 반응하는 강한 상관과 계정별 기저율 1~11%를 둔 정직 6000계정×300쌍에서 P(언젠가 E ≥ 5/20/100) ≤ 1/x(3σ 여유), 반응 0.8 대 0.04인 부정 사용자는 평균 60쌍 안에 확정, 규칙 BOTH/PAIRED 동작, SQLite 저장·1차 스키마 마이그레이션.
- 효과(위 표, 신뢰100%·필터 끔): 밀도 E에서 혼합 98% · 2.4분, 쌍 정확 75% · 83.3분, 기본 규칙 94% · 42.8분. D에서 64% · 66.0분 / 18% · 105.4분 / 58% · 81.9분.
  쌍 정확은 느리다: 불일치 쌍 하나가 주는 증거가 최대 log10 2 = 0.30이라 10⁹까지 최소 30쌍이 필요하다(혼합은 p₀=0.017 대비 반응 하나가 큰 배수). 대신 정직 오탐이 정확히 통제된다(아래).
  기본 규칙이 쌍 정확 단독보다 빠른 이유는 문턱이 10³(최소 10쌍)이기 때문이다.
- 대안 혼합과 쌍 정확의 평균(E = 평균)은 큰 쪽에 지배돼 혼합과 같게 나오고(E, 신뢰100%: 97% · 2.4분) 혼합의 오탐도 물려받는다. 그래서 채택하지 않았다.

- **원인(측정한 것)**:
  1. **플레이 방식별 정직 반응률이 다르다.** D: 동굴 탐색 미끼 0.18%/위약 0.18%, 브랜치 마이닝 2.44%/2.45%, 합친 위약률 0.85% → p₀ = 0.0170. 브랜치의 실제 반응률(2.4%)이 p₀(1.7%)를 넘어 E가 자란다(브랜치 ≥ 2가 D 40.7%, E 70.4%).

  3. e-value 구현 오류는 아니다: p = p₀에서의 타당성 테스트는 통과하고, 위 1·2는 그 테스트가 가정한 조건(반응 확률 ≤ p₀, 조건부 독립)의 위반이다. 2번의 크기와 1번의 크기를 분리하는 실험은 하지 않았다.
- 대응: 기본 확정 규칙을 `BOTH`로 했다. 오탐은 쌍 정확 문턱 10⁻³ 이하로 정확히 묶이고(6000계정 0건) 혼합은 검출력만 담당한다. 플레이 방식별 p₀는 구현하지 않았다.

### 남은 한계

1. **[1.2단계에서 닫힘 → 1.2절] 패킷 경로·1틱 지연에 무력(0%).** 위 3절. 청크 패킷을 바꾸지 않고 블록 갱신으로 보내는 한 구조적이다. 청크 데이터에 넣는 방식은 서버 코어가 필요하다(Paper 내장 anti-xray가 그런 방식이라고 알고 있으나 이번에 문서로 확인하지 않았다).
2. **[1.2단계에서 이벤트 순서 문제는 사라지고 다른 미검증이 생김 → 1.2절] 실서버 미검증.** `PlayerChunkLoadEvent`가 청크 패킷 송신 전인지 후인지 문서에 없다. 전이면 미끼 패킷이 청크보다 먼저 가서 무시될 수 있고, 1틱 뒤에 보내면 시점 필터에 걸린다(시뮬레이터: 1틱 지연이면 0%). 클라이언트가 두 패킷을 같은 틱에 처리하는지도 확인하지 못했다.
3. **밀도가 높아야 잡힌다.** D에서 신뢰100%·검증형이 58~76%(중앙값 67~84분 채굴), 신뢰50%는 2~5%, 신뢰20%는 0%. E는 신뢰100%·검증형 92~99%(중앙값 34~51분)이지만 그때도 미끼 뭉치가 청크당 1.8개 대 진짜 4.4개(미끼 몫 약 29%)라서 광맥 모사가 진짜에 가까워야 의미가 있다. 비용은 위 표.
4. **[1.2단계에서 보정 → 1.2절] 미끼 높이 분포가 밀도가 높을수록 어긋난다**(2절). 통계 필터를 쓰는 엑스레이(청크 여러 개의 y 히스토그램)는 시험하지 않았다.
5. **[1.2단계에서 해결 → 1.2절] 청크를 다시 받으면 미끼 위치가 바뀐다.** 진짜 광석은 고정이라, 청크를 캐시하는 클라이언트는 "재방문 때 달라진 광석"을 알아챌 수 있다. 대응하지 않았다.
6. **[1.2단계에서도 그대로 → 1.2절] 혼합 e-value 단독은 여전히 상관·이질성에 무너진다**(5절). 기본 규칙이 쌍 정확 문턱으로 막지만 그 대신 확정이 느리다. 플레이 방식별 p₀는 다음 과제.
7. **시뮬레이터는 모델이다.** 엑스레이 정책(가장 가까운 광석), 시야 32블록, 청크 반경 4, 진짜 광맥의 바닐라 근사, 정직 두 가지 플레이 방식은 내가 정했다. 사람 데이터가 아니다. 진짜 광맥 밀도를 바닐라 근사로 잡아 청크당 4.4개인데 실제 서버와 다를 수 있고, 다르면 미끼 몫과 검출력이 달라진다.
8. 이 단계의 기존 테스트 27개는 API 변경(`Display`, `Params`, 청크 전송 배치)에 맞춰 호출부를 고쳤다. 검사 내용은 같고, `coinFlipIs…`의 평균 거리 차이 임계값만 고정 0.5에서 표준오차 4배로 바꿨다(0.5는 표준오차 1.3배 정도라 시드에 따라 흔들렸다).

## 1.2단계: 0% 채널 닫기 (청크 데이터 패킷에 미끼 직접 삽입, 재방문 일관성, 먼저 반응한 쪽 검정)

### 한 줄 결과

- **닫혔다(시뮬레이터).** 미끼를 청크 데이터에 넣으면 패킷 경로 필터·시점 필터(허용 0틱)·재방문 차이 필터가 있어도 검증형이 잡힌다. 같은 필터가 1.1 방식(블록 갱신 패킷)에는 0%였다. 표는 3절.
- **대가가 있다.** 미끼 쌍은 한 번만 반응 기회를 가지므로(재방문마다 새로 뽑을 수 없다) 밀도가 낮으면 못 잡는다. 청크당 미끼 0.04~0.06개(A·B)는 전 전략 0%, 1개(D)는 신뢰100%·검증형 30~40%, 2개(E, 새 기본값)는 89~98%, 4개(F)는 100%.
- **오탐은 F에서 정직 6000계정 중 BOTH 1건**(0.02%, 이론 한계 0.1% 이하)이다. 목표였던 "0건"은 F에서 못 지켰다(6절).
- 실서버(Paper 26.2 + PacketEvents)에서는 실행해 보지 못했다. 확인 순서는 8절.

### 0. PacketEvents 버전 확인

- **2.14.0**(2026-09-23)이 최신 안정판이다. 근거: GitHub 릴리스 페이지(2.14.0은 MC 26.3 지원 명시, 2.13.0은 26.2, 2.12.x는 26.1 지원 명시, 모두 정식 릴리스)와 `docs.packetevents.com/development-setup`의 좌표
  (`com.github.retrooper:packetevents-spigot:2.14.0`, 저장소 `https://repo.codemc.io/repository/maven-releases/`). 내려받은 2.14.0 jar의 `ServerVersion`에 `V_26_2`가 있음을 `javap`로 확인했다.
  2.14.0 릴리스 노트가 26.2를 명시하는지는 확인하지 못했다(요약에 26.3만 나왔다).
- `compileOnly`로 넣어 플러그인 jar(107,850바이트)에는 안 들어간다. 서버에는 PacketEvents 플러그인을 따로 설치하고 `plugin.yml`에 `depend: [packetevents]`. 다른 외부 라이브러리는 추가하지 않았다.
  테스트는 PacketEvents 정적 초기화가 요구하는 `PacketEventsAPI`를 추상 메서드만 비운 최소 구현으로 채워(netty·서버 클래스 없이) 실제 `Column`·`Chunk_v1_18` 객체를 돌린다.

### 1. 청크 패킷 미끼

흐름(`PacketDecoyListener`, 패킷을 만드는 스레드에서 실행):
1. `CHUNK_DATA` 패킷을 읽어 `Column`을 얻는다. 미끼를 넣을 수 있는 플레이어(서바이벌·모험, 표에 등록됨)가 아니면 건드리지 않는다.
2. `PacketChunkView`(패킷이 담은 블록 상태로 만든 `BlockView`, 이 청크만 보이고 이웃 청크는 "로드 안 됨")로 `engine.prepareChunk`를 부른다. 서버 월드를 읽지 않으므로 스레드 안전하다.
   `DecoyGuard.sealed`가 이 시야에서 뭉치의 모든 블록을 검사하고, 통과한 미끼 블록만 돌려준다.
3. `ChunkPatcher`가 쓰기 **직전에 같은 `DecoyGuard`로 한 번 더** 검사한다. 하나라도 어긋나면 아무것도 쓰지 않는다(일부만 써서 추적에 없는 미끼가 나가지 않게). 통과하면 그 플레이어의 패킷 데이터 안 블록 상태를
   가짜 다이아 광석(바탕이 심층암이면 심층 다이아 광석)으로 바꾸고 다시 인코드하게 표시한다.
4. 메인 스레드로 넘겨 `engine.registerChunk`가 쌍을 추적에 올리고 **실제 월드로 봉인을 한 번 더 검사**한다(패킷을 만든 뒤 월드가 바뀌었을 수 있다). 깨졌거나 플레이어가 자격을 잃었거나 월드가 달라졌으면 이미 나간 미끼를
   진짜 블록으로 되돌린다. `sendBlockChange` 계열은 이 회수에만 쓴다. 서버 월드는 어디서도 바꾸지 않는다.
5. 이 리스너가 예외를 내도 청크 전송을 막지 않는다(수정 없이 나간다).

블록 상태 분류(`PacketStateTable`)는 서버가 켜질 때 메인 스레드에서 모든 `Material`을 분류해 이름으로 조회만 한다. 규칙은 `BukkitBlockView`와 같은 것(불투명·안정)이라 패킷 시야와 실제 월드 시야의 판정이 일치한다.
`PlayerChunkLoadEvent`는 이제 광맥 표본을 배우는 데만 쓴다(패킷 스레드가 Bukkit API를 만지지 않도록 플레이어의 월드·자격은 `PlayerRegistry`가 1초마다·이벤트마다 갱신).

테스트(`ChunkPatcherTest`, 실제 PacketEvents 청크 객체): 바뀐 블록이 정확히 계획한 미끼 블록이고, 바꾸기 전 데이터에서 여섯 면이 전부 불투명이었고, 청크 경계 밖 이웃에 기댄 미끼가 없고, 계획에 없는 블록과 위약 자리는 그대로이고,
같은 청크를 다시 받으면 인코드한 패킷 바이트가 완전히 같고, 다른 플레이어는 다르고, 조작된 패치(공기와 붙은 자리)는 쓰기를 거부하며 데이터를 하나도 안 바꾼다.

### 2. 재방문 일관성

- **결정적 계획**: 좌표·모양·동전을 `HMAC-SHA256(서버 비밀 시드, 플레이어|월드|청크|슬롯)`로 만든 난수열에서 뽑는다(`Seeds`, JDK 기본 제공). 시드는 `config.yml`의 `secret-seed`(비어 있으면 처음 켤 때 생성·저장)이고
  어떤 로그·명령에도 출력하지 않는다(값이 바뀌면 자리가 전부 바뀐다, 서버를 다시 켜야 적용). 플레이어 위치·동시 개수·쿨다운은 결정성을 깨므로 없앴다(`min-distance`, `max-active-pairs`, `cooldown-seconds` 삭제, 밀도는 `pairs-per-chunk` 하나).
- **기억**: 플레이어별 계획을 (최대 8192청크) 기억해 같은 청크를 다시 받으면 같은 자리·같은 동전을 쓴다(`RevisitTest`: 세 번 재방문해도 미끼·위약 좌표가 완전히 같음).
  기억에는 쌍의 상태가 있다: **회수됨**(노출로 거둠: 다시 안 보냄), **판정 완료**(다시 받으면 미끼는 보이되 새 관측을 안 만듦), 그 밖은 언제든 복원.
- **미끼가 저절로 사라지지 않는다**: 1.1까지는 판정 창이 끝나면 미끼를 화면에서 거뒀다. 진짜 광석은 시간이 지나도 사라지지 않으므로 그것이 단서라 화면에 그대로 둔다(`windowExpiryJudgesMissButKeepsTheDecoyOnScreen`). 노출 회수와 청크 언로드만 미끼를 없앤다.
- **청크 언로드는 판정이 아니다**(이 단계에서 고침): 재방문을 결정적으로 하자 같은 쌍이 도달 전에 언로드로 반복해서 VOID가 되어 쌍이 안 끝나는 문제가 생겼다(창 240초에서 확정률이 27%, 480초에서 100%로 갈렸다). 언로드는 이제 판정 없이 "화면에 있던 시간"을 쌍에 더하고,
  다시 받으면 이어서 창을 잰다. 두 자리가 같은 시간을 겪으므로 쌍은 항상 끝난다. 접속을 끊으면 판정 전이던 자리는 VOID다(`exposureTimeAccumulatesAcrossUnloadsAndBothArmsResolveMissTogether`).
- 측정: 시뮬레이터에서 청크 전송의 95%(2,286,013회 중 2,171,238회)가 재방문이다(청크 경계를 오가며 다시 받음). 그래서 계획 기억이 핵심이다. 재방문에서 엔진 처리는 처음의 1/6~1/8이다(3절 표).
- **재방문 차이 필터 대조군**: 재방문마다 새로 뽑는 1.1 방식(`--reroll`)에서는 이 필터가 통한다(D: 기본 규칙 86% → 10%, F: 먼저 반응 100% → 39%). 결정적 배치에서는 통하지 않는다(4절).

### 3. 판정과 쌍 검정 수정 (1.1을 뒤집은 것)

측정 중 1.1의 쌍 정확 검정이 결정적 재방문 아래에서 거의 확정하지 못함을 발견해 고쳤다(1.1 정의: 두 자리가 다 판정된 뒤 한쪽만 반응한 쌍. 이 정의로는 모든 밀도·전략에서 확정 0~4%).

- **먼저 반응한 쪽 검정**: 반응(HIT)이 나온 쌍마다 첫 반응이 미끼였나 위약이었나를 센다. 귀무(미끼 표시가 반응에 영향 없음)에서 동전이 조건과 독립이라 "미끼가 먼저"는 정확히 1/2이고, 짝의 다른 쪽이 판정될 때까지 기다리지 않으며
  p₀도 독립성도 필요 없다. 두 자리의 가장 가까운 블록 사이가 2r+2(=8블록) 이상이라 (반응 반경의 두 배보다 멀어) 한 순간에 둘 다 반응하는 일은 없다. e-value는 1.1과 같은 격자 혼합(`Mixture.observePaired`).
  정직 계정 6000×300쌍에서 두 자리 반응 시각이 강하게 상관돼도 P(언젠가 E ≥ 5/20/100) ≤ 1/x임을 테스트한다(`firstReactionEvalueIsValidForHonestPlayersWithCorrelatedReactions`). 1.1의 "한쪽만 반응" e-value는 진단용으로 남겼다.
- **창 이후의 첫 반응(LATE_HIT)**: 판정 창(MISS)이 끝난 뒤 처음 반응하면 혼합에는 안 넣고 먼저 반응한 쪽 검정에만 센다. 창은 혼합이 반응률을 재는 단위일 뿐이고, 이 검정은 언제든 처음 나온 반응을 센다.
  판정이 끝난 쌍을 다시 받아도 반응이 한 번도 없었으면 두 자리를 계속 지켜본다(`LateHitTest`). 창을 길게 잡으면 확정률이 오르는 것을 예비 측정에서 봤지만(창 480초에서 BOTH 100%, 다른 판정 정의였다) 창은 혼합이 반응률을 재는 단위이기도 해서 창은 그대로 두고 이 방법을 택했다.
- **BOTH 재정의**: 혼합이 E ≥ 1/α를 한 번이라도 넘었고 먼저 반응한 쪽이 E ≥ 1/paired-alpha(10³)를 한 번이라도 넘었으면 확정(`AccountRecord.ever`). 두 e-과정 모두 "언젠가 넘음"이 타당성의 조건이라 이렇게 묶는다.
  동시에 넘어야 하면 혼합이 MISS 관측으로 내려간 뒤에는 확정이 안 된다. 오탐은 먼저 반응한 쪽 문턱 10⁻³ 이하로 정확히 묶인다.

### 4. 높이 분포 보정

1.1에서는 밀도가 높을수록 미끼가 위로 몰렸다. 후보가 조건(봉인·간격·월드 범위)을 통과할 확률이 높이 띠마다 다르기 때문이다. `YBalance`가 띠(8칸)별 통과율을 재고 통과한 후보를 (가장 낮은 띠의 통과율 / 그 띠의 통과율) 확률로만
받아들여 띠별 최종 통과율을 같게 만든다(`heightBalanceMakesAcceptedHeightsFollowTheSourceDistribution`). 정직 코호트 1000계정에서 진짜 광맥 6,639개(월드 6종 전체)와 첫 방문에서 청크 데이터에 들어간 미끼 뭉치(D 114,775개, E 229,550개, F 458,182개; 같은 청크를 다시 받아 들어간 것은 다시 세지 않는다)를 비교했다:

| D (1) | 켬 | **0.036** | −36.4 | 0.030 |

### 5. 레드팀 재측정 (청크 패킷 경로, 기본 규칙 BOTH)

전략 5종(신뢰 100/50/20%, 검증형 3/10번)에 필터를 켠·끈 상태, 각 200계정, 최대 120분 채굴. 필터: **시점**(허용 0틱), **모양**(단일·13 이상 무시), **재방문 차이**(처음 받은 데이터에 없던 광석 무시, 클라이언트가 청크를 캐시한다고 가정),
**패킷 경로**(블록 갱신 패킷으로 온 광석 무시), **전부**(시점+모양+재방문+패킷 경로). 대조군: 같은 미끼를 1.1 방식(별도 블록 갱신 패킷)으로 보낼 때(같은 배치·같은 밀도라 경로만 다르다). 셀은 "확정률 · 확정까지 채굴 시간 중앙값".
밀도는 청크당 시도하는 쌍 수 `pairs-per-chunk`: A 0.04, B 0.06, D 1, E 2(새 기본값), F 4. 실측 청크 전송당 미끼 뭉치 수는 A 0.040, B 0.060, D 1.000, E 1.999, F 3.990개(진짜 광맥은 청크당 약 4.3개)다.
(1.1의 A~E는 쌍 상한·쿨다운으로 정했으나 결정적 계획에서는 그 개념이 없어서 1.1의 측정 밀도와 맞춰 다시 정의했다.)

### 6. 오탐 재확인 (정직 6000계정, 각 최대 60분)

밀도별 별도 실행(시드 31~35). 셀은 정직 계정 중 그 문턱에 **한 번이라도** 닿은 비율(계정 수). 이론상 P(언젠가 E ≥ x) ≤ 1/x: log10E ≥ 2는 1% 이하여야 한다.

| 밀도 | 혼합 log10E ≥ 2 | 먼저 반응한 쪽 ≥ 1 / **≥ 2** / ≥ 3 | 한쪽만 반응(1.1 정의) ≥ 1 / ≥ 2 | 혼합 단독 확정(10⁹) | **BOTH 확정** |

| A (0.04) | 0.02% (1) | 0 / **0** / 0 | 0 / 0 | 0 | **0** |

- **먼저 반응한 쪽 e-value P(log10E ≥ 2)는 모든 밀도에서 1% 이하**(최대 0.22%)이고 ≥ 1도 10% 이하(최대 5.92%)다.
- **BOTH 확정은 A·B·D·E에서 0건, F에서 1건**(0.017%)이다. "0건" 목표는 F에서 못 지켰다. 이 결과는 문턱 10⁻³이 허용하는 범위(6000계정에서 기대 최대 6건) 안이고 다른 문턱은 재지 않았다.
  F에서 0건을 안정적으로 지키려면 `paired-alpha`를 10⁻⁴로 내려야 하는데 그 경우의 확정 시간은 재지 않았다.
- **혼합 단독은 밀도 D 이상에서 이론 한계를 크게 넘고(15.68~53.15%) F에서는 789계정(13%)이 10⁹를 넘어 확정된다.** 원인은 1.1과 같다: 플레이 방식별 정직 반응률 차이(브랜치 마이닝이 동굴 탐색의 6~10배)와 반응의 뭉침.
  혼합 단독으로는 안전하지 않으므로 BOTH를 기본으로 둔다.

### 8. `/anchor debug <플레이어>`와 실서버에서 확인할 순서

`/anchor debug <플레이어>`(권한 `anchor.admin`, 접속 중인 플레이어만): 그 플레이어에게 **계획된** 미끼·위약의 개수와 상태별 합계(활성·판정 완료·회수됨·대기(청크 밖)), 그리고 가까운 40개의 `[미끼|위약] 월드 (x, y, z) N블록 · 거리 | 상태`.
상태: **활성**(판정 전, 화면에 있음), **판정 완료(HIT/MISS, 화면 유지)**, **회수됨(다시 안 보냄)**, **대기(청크 밖: 다시 받으면 복원)**, 판정 완료(청크 밖). 좌표가 그대로 나오므로 관리자 전용이고 시드는 절대 안 나온다(`RevisitTest.debugListsEveryPlannedSiteWithAStatus`).

실서버 확인 순서:
1. PacketEvents 2.14.0 플러그인 설치 → 서버 콘솔에서 PacketEvents가 켜지고 이 서버 버전을 지원한다고 나오는지 확인. anchor-mc를 넣고 켠다: 콘솔에 "secret-seed가 비어 있어 새로 만들어 저장했다" 경고(값 없음)가 한 번 뜨고 `config.yml`에 시드가 생겼는지 확인.
2. 서바이벌로 접속해 지하로 내려가 몇 청크 이동 → `/anchor stats`: "청크 패킷에 미끼 삽입 N회(실패 0회)"에서 N이 늘어야 한다. 실패가 0보다 크면 콘솔의 "청크 패킷 미끼 삽입 실패" 로그(최대 3줄)를 그대로 알려 달라.
3. `/anchor debug <나>`: 가까운 자리의 좌표와 상태가 "활성"으로 나오는지. 접속 직후 처음 받은 청크는 플레이어 표가 채워지기 전이라 미끼가 없을 수 있다(그 청크를 벗어났다 돌아오면 생긴다).
4. **미끼가 실제로 클라이언트에 왔는지**: X-ray 리소스 팩(돌을 투명하게)을 쓰는 클라이언트로 debug가 알려 준 좌표를 본다. 그 자리에 다이아 광석이 보여야 하고, 그 자리가 위약이면 안 보여야 한다.
5. **재방문 일관성**: 시야 거리 밖으로 멀어졌다가 돌아온 뒤 `/anchor debug`를 다시 → 같은 좌표가 "대기"에서 "활성"으로 돌아와야 하고, X-ray 팩으로 같은 자리에 광석이 다시 보여야 한다.
6. **회수**: 미끼 옆 블록을 캐서 이웃을 노출시키면 광석이 진짜 돌로 돌아가고 debug 상태가 "회수됨"이 되어야 한다. 멀어졌다가 돌아와도 그 자리에 광석이 없어야 한다(다시 안 보냄).
7. **경로**: 미끼가 청크와 같은 패킷에 오는지는 클라이언트 쪽에서 봐야 한다(예: 패킷 로거 모드가 그 좌표를 블록 갱신 패킷이 아니라 청크 데이터에서 보는지). `sendBlockChange`가 나가는 것은 회수뿐이어야 한다.
8. 부하: `pairs-per-chunk`를 1 → 2 → 4로 올리며 mspt와 접속 직후 스파이크를 본다. 기대(계산값): 청크 하나 약 1 ms 안팎이 netty 스레드에 든다.

| 1.1절 밀도 A~E(쌍 상한·쿨다운으로 정의), 설정 `min-distance`·`max-active-pairs`·`cooldown-seconds` | 결정성 때문에 삭제, 밀도는 `pairs-per-chunk` 하나. A 0.04, B 0.06, D 1, E 2(새 기본), F 4 |
| 1.1절 §5: 지시한 설정(쌍 6, 쿨다운 5초)에서 정직 오탐 통과 | 그 설정은 없어졌다. 새 밀도에서는 BOTH 오탐 A·B·D·E 0건, F 1건 |

### 남은 한계

1. **실서버 미검증.** PacketEvents가 이 서버(Paper 26.2)에서 `CHUNK_DATA`를 읽고 다시 쓰는 것, `User#getDimensionType().getMinY()`, 접속 직후 청크, 월드 이동 직후 청크의 월드 이름은 실서버에서 확인하지 못했다.
   월드 이름은 `PlayerRegistry`(메인 스레드가 갱신)에서 읽기 때문에 월드를 옮긴 직후에는 잠깐 어긋날 수 있고, 어긋나면 등록 단계가 이미 나간 미끼를 되돌린다(불변식은 지키지만 그 청크에는 미끼가 안 남는다).
2. **ViaVersion 등으로 다른 버전 클라이언트가 접속하면** 블록 상태 번호 체계가 달라 패킷 삽입이 맞는지 확인하지 못했다(서버 버전 번호를 그대로 쓴다).
3. **패킷에는 이 청크의 데이터만 있어서** 청크 가장자리 블록과 이웃 청크에 걸치는 자리는 후보가 못 된다(진짜 광맥은 걸친다). 미끼는 청크 안에만 놓이고 청크 경계에 가까운 곳은 드물다.
4. **밀도가 낮으면 못 잡는다**(A·B 0%, D는 신뢰50% 이하 사실상 불가). 새 기본값 E(청크당 2)는 신뢰100%·검증형 89~98%, 신뢰50% 46~55%, 신뢰20% 6~9%다. F(4)는 미끼가 진짜 광맥과 비슷한 수(청크당 4.0대 4.3)가 되어 **청크당 광석 개수 통계로 구별될 수 있으나 그 필터는 시험하지 않았다**.
5. **비밀 시드가 서버에 있는 한**: 시드가 유출되면 미끼 위치를 계산할 수 있다. 계획·회수 기억(회수됨·판정 완료)은 메모리에만 있어서 서버를 다시 켜면 사라지고, 광맥 표본(뱅크)도 다시 배우므로 재시작 뒤에는 같은 청크의 미끼가 달라질 수 있고 회수됐던 쌍이 (봉인이 여전하면) 다시 나갈 수 있다.
6. **높이 분포**는 표본 뱅크(600개)를 따른다. 표본의 평균 오차(약 1.4)가 남는다(`sites.profile-samples`를 늘리면 줄지만 스캔 비용이 는다, 재지 않았다).
7. **BOTH 오탐이 F에서 1건**(6절). 혼합 단독은 D 이상에서 안전하지 않다.
8. **시뮬레이터는 모델이다.** 청크 경계를 오가는 재방문이 95%라는 것은 시뮬레이터의 클라이언트 이동·언로드 모델(반경 4청크, 즉시 언로드)의 결과이고 실서버(시야 10청크 이상, 언로드 시점)는 다를 수 있다. 엑스레이 정책(가장 가까운 광석, 시야 32블록), 재방문 차이 필터가 전제하는 "클라이언트가 청크를 캐시함",
   진짜 광맥 밀도의 바닐라 근사, 정직 두 가지 플레이 방식은 내가 정한 값이다. 사람 데이터가 아니다.
9. **CPU 수치는 합성 지형**(섹션당 10종 상태)이고 실제 서버의 청크 패킷 크기·팔레트 분포는 다르다. 바이트의 팔레트 경계 최악값이 실제로 얼마나 자주 나오는지는 모른다.
10. 이 단계에서 기존 테스트 27개(1.1 기준 48개 중)는 API 변경에 맞춰 호출부와 기대를 고쳤다: 만료·언로드 관련 기대(VOID → 판정 없음, MISS 후 화면 유지), 재검사 호출(먼 자리는 10번에 한 번). 검사하려는 불변식은 그대로다.

### 관측

### 코드로 확인한 원인 후보 (실서버 사유 집계는 아직 없다)

| 후보 | 코드 확인 | 결과 |

### 수정
1. **회수 사유 기록.** `RetireCause`(12종)와 `Reason`(사유, 좌표·블록 종류·청크 로드 여부, 틱). 모든 거둠은 사유가 반드시 있다(`ResponseTracker.retire`가 null이면 거부).
   사유: `PACKET_UNSEALED`, `REGISTER_UNSEALED`, `PERIODIC_BREACH`, `CHUNK_LOAD_BREACH`, `BLOCK_EVENT`, `TOO_CLOSE`(영구 회수) / `INELIGIBLE`, `REGISTER_NOT_ALLOWED`, `LEFT_WORLD`, `QUIT`, `CHUNK_DROPPED`, `SHUTDOWN`(화면에서만 거둠, 계획 유지).
2. **`/anchor stats`** 끝에 "회수 사유별(쌍 단위): 이름(설명) 횟수 ... || 판단 보류 중인 활성 자리 N". **`/anchor debug`**는 같은 요약을 먼저 찍고, 상태에 사유를 붙인다: `회수됨(다시 안 보냄) · 사유: 주기 검사: 이웃이 불투명 고체가 아님 — 자리 (x, y, z)의 이웃 (x, y, z) 블록=DIRT, 청크(cx, cz) 청크 로드=true, 뚫림`. 계획이 남은 거둠은 `대기(...) · 마지막 거둠 사유: ...`.
3. **자격 상실은 영구 회수가 아니다.** 화면에서만 거두고(판정 없음, 노출 시간 정지) 계획은 남긴다. 서바이벌로 돌아와 청크를 다시 받으면 같은 미끼가 돌아온다. 크리에이티브인 동안은 미끼를 넣지 않는 것은 그대로다.
4. **인접 청크 정책: 판단 보류.** `DecoyGuard.check`는 봉인됨/뚫림/모름 셋을 구분한다(뚫림이 모름보다 우선). 모름은 이웃 좌표의 청크가 로드 안 됐을 때뿐이다.
   - **새로 보낼 때(계획·`prepareChunk`·`ChunkPatcher`)는 `sealed()` = 봉인됨만 통과**한다: 모름도 불허. 불변식 1·3은 그대로다(테스트 `guardDistinguishesBreachFromUnknownNeighbor`가 "모름이면 `sealed()`는 false"를 확인).
   - 이미 나간 자리의 주기 검사(`verifyAll`)는 뚫림만 거두고 모름은 보류한다(`판단 보류 중`으로 표시).
   - 보류하던 이웃 청크가 서버에 로드되면(`ChunkLoadEvent`) `onChunkLoaded`가 그 청크와 이웃 청크에 걸친 자리를 **바로** 다시 검사해, 그사이 이벤트 없이 바뀌어 실제로 노출됐으면 그때 거둔다(`CHUNK_LOAD_BREACH`).
   - 등록 단계(`registerChunk`)도 같다: 뚫림이면 회수, 모름이면 추적하고 보류.
5. **동시성.** `PlannedPair` 상태 전이를 한 자물쇠 아래로. 사유 집계는 쌍이 처음 접힐 때 한 번만 센다.

### 재현 테스트 (수정 전 실패 확인 → 통과)
수정 전 코드에서 두 재현 테스트가 실패하는 것을 먼저 확인했다(`losingEligibilityDoesNotRetirePlansForever`: "자격 상실이 계획을 영구 회수로 표시했다", `periodicCheckHoldsWhenChunkIsNotLoaded`: "로드 안 된 청크를 이유로 자리를 회수했다"). 수정 뒤 통과한다.
`RetirementCauseTest`(6개): 위 둘 + `heldSitesAreRetiredWhenChunkLoadsAndIsActuallyExposed`(불변식 3: 보류 뒤 로드됐을 때 실제 노출이면 회수하고 되돌리기 패킷이 나감) + `guardDistinguishesBreachFromUnknownNeighbor` + `everyRetirementRecordsCauseAndDetail`(좌표·재질 설명·청크 로드 여부·집계) + `terminalRetirementCannotBeUndoneByLateConsume`.
전체 78개 통과(기존 72개 그대로, 기존 테스트는 수정하지 않았다).

### 실서버에서 다시 확인할 방법
1. 새 jar를 넣고 서버를 켠다(PacketEvents 2.14.0 그대로). **서바이벌**로 접속해 같은 곳까지 내려간다(크리에이티브로 바꾸는 것은 마지막에).
2. `/anchor stats` → 마지막 줄 "회수 사유별". 서바이벌로 파고 내려가는 동안 `INELIGIBLE`이 0이고 회수됨 총합이 작아야 한다. `PACKET_UNSEALED`·`REGISTER_UNSEALED`·`PERIODIC_BREACH`가 많으면 `/anchor debug`로 그 자리의 사유 문장(이웃 좌표·블록 종류)을 알려 달라. **블록 종류가 tuff·calcite·deepslate 계열 등 "고체여야 하는" 재질인데 `(isOccluding=false)`가 붙어 있으면 26.2의 `isOccluding` 문제다.**
3. `/anchor debug <나>`: 활성이 0이 아니어야 하고, 거리 10블록 안 자리가 "활성"이어야 한다.
4. 이제 `/gamemode creative` → `/anchor stats`에서 `INELIGIBLE [계획 유지]`가 늘고 debug가 "회수됨"이 아니라 "대기 · 마지막 거둠 사유: 플레이어 자격 상실"이어야 한다. 다시 `/gamemode survival` 뒤 멀어졌다 돌아오면(청크 재전송) 같은 좌표가 "활성"으로 돌아온다.
5. "판단 보류 중인 활성 자리"가 0보다 크면 그 자리들은 자기 청크가 서버에 로드 안 된 채 클라이언트가 갖고 있는 것이다. 청크가 로드될 때 `CHUNK_LOAD_BREACH`가 있으면 실제로 그사이 바뀐 것이다.
6. 코드로 확정하지 못한 것: 원래 1832건이 위 원인 중 무엇이었는지. 위 순서 2에서 **사유 집계가 회수 사유를 확정**한다.

### 실서버 2차 확인용 추가: 관전자 옵션, 자격 회복 복구, 삽입 카운터

**관전자 허용 옵션(테스트 전용).** `config.yml`의 `debug.allow-spectator`(기본 `false`). `true`면 관전자 모드 플레이어도 미끼 자격을 잃지 않아 화면에서 거두지 않는다(관전자로 벽 속을 날며 미끼가 보이는지 눈으로 확인). 크리에이티브는 옵션과 무관하게 자격이 없다.
관전자 상태의 반응은 증거에 넣지 않는다: 판정(HIT/MISS/VOID)과 쌍 상태 갱신을 모두 버리고 표시만 유지한다(그 사이 판정된 자리는 서바이벌로 돌아와도 증거가 되지 않는다). 켜져 있으면 서버 시작·`/anchor reload`마다 콘솔에 경고 상자, `/anchor stats` 첫 줄에 "디버그: 관전자 허용 중". 규칙은 `Eligibility.eligible`(테스트 `eligibilityMatrix`).

**자격 회복 시 미끼 복구.** 죽거나 게임모드가 바뀌어 자격을 잃으면 미끼를 화면에서만 거두고(`INELIGIBLE`) 그 쌍을 "정지 목록"에 둔다. 리스폰·게임모드 복귀(이벤트 한 틱 뒤)·매초 틱에서 자격이 돌아온 것을 보면 **청크를 다시 받지 않고** 블록 갱신 패킷(`Display.show`)으로 다시 보여 주고 추적에 올린다.
복구 직전에 그 쌍을 **실제 월드에서 불변식 1로 다시 검사**한다: 봉인됨만 보낸다, 뚫렸으면 영구 회수(`REGISTER_UNSEALED`), 모름(이웃 청크 로드 안 됨)이면 보내지 않고 계획만 둔다(청크를 다시 받을 때 돌아온다). 정지 목록에서 클라이언트가 버린 청크(`PlayerChunkUnloadEvent`)·서버가 내린 청크·월드 이동은 빠진다. 통계: `/anchor stats`의 "자격 회복으로 다시 보인 쌍". 테스트: `RecoveryTest`.
**한계(이 경로는 청크 재전송 기반이 아니다).**
1. 재전송 경로는 미끼가 청크와 같은 패킷에 오지만 이 경로는 별도 블록 갱신 패킷이다. 미끼가 청크보다 늦게 도착하므로 1.1단계에서 본 "블록 갱신 채널은 시점·패킷 경로 필터에 걸린다"가 이 경로에는 다시 적용된다. 복구된 미끼는 그 필터를 쓰는 엑스레이에 덜 유효하다.
2. 클라이언트가 그 청크를 실제로 가졌는지는 `PlayerChunkUnloadEvent` 기록에 기대는 추정이다. 이벤트를 놓치면 클라이언트가 무시하는 패킷을 보낼 뿐 노출은 없다(블록 갱신은 미끼 종류 블록만 보낸다).
3. 복구 순간 이웃이 뚫려 있으면 그 쌍은 영구히 접힌다(재전송에서도 안 돌아온다). 안전 쪽의 선택이다.

**"청크 패킷에 미끼 삽입 473회"가 재시작 전후 같았던 것.** 이 카운터(`PacketDecoyListener.patched`)는 `AtomicLong`을 0으로 만든 메모리 값이고 어디에도 저장되지 않는다(테스트 `CounterTest`가 소스로 확인). 플러그인 인스턴스가 새로 켜지면 0에서 시작하므로 **저장된 값이 아니고, 갱신이 안 되는 버그도 아니다.** 같은 숫자가 다시 나온 이유로 코드에서 설명되는 것은 하나뿐이다: 미끼 자리는 (플레이어, 청크, 비밀 시드)로 결정적이라 같은 계정이 같은 곳에서 같은 방식으로 접속해 받은 청크 수가 같으면 미끼가 들어간 청크 수도 같다. (플러그인을 `/reload`처럼 켜지 않고 그대로 뒀다면 값이 이어지는 것도 정상이다.) 헷갈리지 않게 stats 문구를 "이번 기동 이후 … (재시작하면 0부터)"로 바꿨다. 재시작 뒤 다른 숫자를 확인하려면 다른 위치로 접속해 보라.

## 실서버 HIT 테스트: 미끼로 직진해 파 들어갈 때

### 관측
서바이벌에서 미끼 (539, -24, 476) 2블록을 향해 남쪽에서 똑바로 파 들어갔다. 미끼는 "회수됨 · 사유: 블록 변경 이벤트 — 변경 좌표 (539, -23, 477) → 자리의 이웃 (539, -23, 476)"이 됐고, 이를 판정 전 회수(증거 제외)로 읽었다. 같은 쌍의 위약은 HIT(테스트용 /fill 방이 바로 위였다).

### 이벤트 순서를 코드로 확인한 결과 (재현되지 않았다)
플레이어가 자리로 한 블록씩 파고 들어가는 순서(이동 → 채굴 → 회수)를 엔진에 재생했다(`DigApproachTest`). **수정 전 코드에서도** 미끼·위약 모두 다음 순서로 동작한다:
1. `BlockBreakEvent`(MONITOR)가 `onPlayerBreak`를 부른다. 이 안에서 `observeDig`(반응 판정)가 **먼저**, `blockChanging`(이웃 자리 회수)이 그 다음이다. 캐는 블록은 이웃이라 자리와 1블록이므로 반응 반경(≥2.5) 안이라 반드시 HIT다.
2. 회수 시점에 자리는 이미 판정이 나 있어(`result`=HIT) VOID를 내지 않는다. 같은 틱이다.
3. 채굴하러 오는 동안 위치 판정(`observePosition`)도 반경 안에 들어오는 순간 HIT를 낸다. 한 블록씩 다가오면 반경 띠(2.0~3.0)를 반드시 지난다.
그래서 관측한 회수 사유가 BLOCK_EVENT였다는 것 자체는 반응이 기록되지 않았다는 뜻이 아니다. **`/anchor debug`가 회수된 쌍에는 판정을 보여 주지 않았기 때문에**(활성 자리에만 "판정 완료(HIT)"를 붙였다) 기록 여부를 볼 수 없었다. 이 절의 첫 수정은 그것이다(아래).
서버에서 실제로 반응이 안 잡혔다면 코드 경로 밖의 원인이다. 후보(미검증): 그 쌍이 이미 위약 HIT로 판정 끝난 쌍이라 재등록 때 미끼 자리가 `hitReported`(먼저 반응한 쪽은 위약)로 등록됨 — 설계상 두 번째 반응은 새 관측이 아니다 / 블록 파괴가 `BlockBreakEvent`가 아닌 경로.

### 실제로 있던 구멍 하나와 수정
1. **반응 띠를 한 걸음에 건너뛰면 VOID로 제외됐다.** `observePosition`은 `d < retract-distance`를 먼저 검사해 판정 전이면 반응 없이 제외했다. 걸음 하나(대각선 1.7블록)로 d 3.3 → 1.6이 되면 반응 띠(2.0~3.0)를 한 번도 못 밟는다. 재현 테스트가 수정 전에 실패했다(HIT 기대, VOID).
   수정: 한 번의 위치 갱신이 `TELEPORT_JUMP`(4블록) 이내인 걸어서 온 이동이면, 밀착 회수 전에 **반응(HIT)을 먼저 기록**하고 같은 틱에 거둔다. 그보다 큰 점프(텔레포트·노클립)는 예전처럼 VOID로 제외한다. 미끼와 위약은 같은 코드(`ResponseTracker`는 kind를 읽지 않는다)라 대칭이다.
2. **채굴 이벤트의 순서를 고정**했다: 위치 기반 반응 판정(`lastPos`) → 채굴 반응 판정 → 회수. 위치 이벤트가 블록 단위로만 오기 때문에 낡은 위치 때문에 반응이 늦는 일을 막는다.
3. **`/anchor debug`에 반응 기록을 항상 붙인다**: `· 반응 기록: 미끼=HIT 위약=없음`(그 쌍의 각 자리가 마지막으로 낸 판정). 회수된 쌍도 보인다. 다음 실서버 확인은 이것으로 판단하면 된다.
4. 다른 이유의 회수는 그대로 증거에서 제외한다: 다른 플레이어의 채굴, 폭발·유체·피스톤(BLOCK_EVENT), 텔레포트 밀착(TOO_CLOSE). 테스트 `otherPlayersDigsAndNonPlayerChangesStayExcluded`, `teleportNextToASiteStaysExcludedFromEvidence`. 불변식 3은 그대로다(회수는 변경 전 이벤트, 같은 틱, `CheckingDisplay`가 검사).

### 시뮬레이터는 이 순서를 놓쳤나
아니다. `Agent.stepTo`가 실서버와 같은 순서다: 막힌 칸이면 `onPlayerBreak`(반응 → 회수)를 먼저 부르고, 그다음 `onMove`. 시뮬레이터 에이전트는 한 칸씩 움직여서 걸음 하나가 1블록을 못 넘으므로 반응 띠를 건너뛰는 일도 없다(d가 3.0 초과에서 2.0 미만으로 가려면 1블록 넘게 줄어야 한다). 그래서 **과대평가가 아니었고 이번 수정은 시뮬레이터 결과를 바꾸지 않는다.**
확인: 같은 시드·조건(`--runs 100 --honest 300 --minutes 120 --seed 1 --ppc 2`)으로 수정 전(HEAD)과 수정 후를 돌렸고 표가 전부 같다. 신뢰100% 끔 BOTH 94%(8.7분), 신뢰50% 42%, 신뢰20% 5%, 검증형(3번) 88%, 검증형(10번) 92%. 정직 코호트 BOTH 확정 0/300(혼합 단독 1건). 참고로 이 실행에서 정직 브랜치마이닝의 혼합 단독 max log10E ≥ 2가 60%로 이론 한계를 크게 넘는데, 수정 전에도 같고 BOTH 규칙이 막고 있다(이전 절의 한계 7과 같은 문제이며 이번 수정과 무관).

### 실서버에서 다시 확인할 방법
1. 서바이벌로 미끼(위약이 아닌 것)를 향해 한 블록씩 곧장 판다. `/anchor debug <나>`에서 그 자리를 본다: `회수됨 · 사유: 블록 변경 이벤트 … · 반응 기록: 미끼=HIT …`이어야 한다. `미끼=없음`이면 반응이 안 잡힌 것이니 그 줄과 `/anchor status`를 알려 달라.
2. 같은 쌍의 위약이 먼저 HIT였던 쌍은 미끼의 반응이 새 관측이 아닐 수 있다: 쌍 상태를 볼 때 위약 반응 기록이 `HIT`인지 먼저 본다. 위약 방 없이 새 쌍으로 시험하는 것이 깨끗하다.
3. 위약으로도 똑같이 판다: `반응 기록: … 위약=HIT`가 나와야 한다(대칭).

## 실서버 자동 테스트: `/anchor simtest`

사람이 직접 파지 않고 실서버에서 HIT 경로를 시험하는 디버그 명령(권한 `anchor.admin`, 기본 op). 판정 로직은 건드리지 않고, 섀도 모드 그대로라 처벌은 없다.

- `/anchor simtest <플레이어> xray <개수>`: 그 플레이어의 **활성 [미끼]** 중 가까운 것부터 `<개수>`개(최대 50, 64블록 이내)를 골라 1블록씩 4틱 간격으로 텔레포트하며 찾아가고, 지나는 발·머리 두 칸과 미끼 자리의 실제 블록을 서버가 `breakBlock`으로 부순다(BlockBreakEvent가 그 플레이어로 불린다). **[위약]은 후보에서 아예 빠진다.**
- `/anchor simtest <플레이어> honest <블록수>`: 미끼·위약 정보를 전혀 안 쓰고 지금 보는 방향(가로 한 축)으로 2칸 높이 직진 채굴.
- 게임모드는 바꾸지 않는다. 서바이벌이 아니어서 판정 대상이 아니면 시작을 거부하고, 도중에 대상에서 빠지거나 나가거나 부술 수 없는 블록(기반암·액체)을 만나거나 파괴가 취소되면 멈춘다.
- 끝나면 요약 한 줄과, 2초 뒤 `/anchor status` 요약을 명령을 친 쪽 채팅에 출력한다.
- 텔레포트는 PlayerMoveEvent를 부르지 않아서, 걸음마다 엔진의 이동 알림(`onMove`)만 대신 부른다(걷는 것과 같게). 이 외의 엔진 호출은 없다.
- 경로 계획은 순수 계산 `SimRoute`(테스트: `SimRouteTest`)로, 한 걸음이 정확히 1블록이고 위약이 안 뽑힘을 확인한다. 실제 서버 동작(텔레포트·블록 파괴)은 Bukkit 없이는 단위 테스트가 안 돼 실서버에서 확인해야 한다.

## 플레이어 기록 초기화: `/anchor reset <플레이어>`

테스트 뒤 그 플레이어를 깨끗한 상태로 되돌리는 명령(권한 `anchor.admin`, 기본 op). **확인 질문 없이 바로 실행**하고, 콘솔에 누가 누구의 어떤 기록(미끼·위약 관측, log10E, 확정 여부)을 지웠는지 경고 한 줄로 남긴다.

- 지우는 것: SQLite의 그 계정 행, 메모리의 누적 e-value 세 가지(혼합·쌍·먼저 반응)와 관측 수·확정 표시, 쌍 대기 상태, 그리고 그 계정의 위약 관측(전체 p₀ 추정에서도 뺀다. 재시작 때 저장소 합계로 다시 읽는 값과 같아진다). 접속 중이 아니어도 저장된 이름이면 된다.
- 배치는 **그대로 둔다**(시드가 같아 같은 좌표): 화면의 미끼는 판정 없이(증거에 아무것도 내지 않고) 되돌리고 그 플레이어의 계획·반응 기록을 비운다. 청크를 다시 받으면 같은 자리가 새 상태로 돌아온다. 그때까지는 미끼가 안 보인다. 통계의 회수 사유는 `RESET`으로 따로 센다(`INELIGIBLE` 진단 수치를 부풀리지 않는다).
- 판정 로직(`ResponseTracker`의 반응·만료 판정, `EvidenceEngine.observe`)은 건드리지 않았다. 테스트: `ResetTest`(증거·저장소), `ResetPlayerTest`(배치·재계획·다른 플레이어 불변).

## 3단계: 정직 브랜치 마이너 오탐의 원인과 수정(창 끝 순서로 쌓기)

### 원인(시뮬레이터 재현, `--sections honest,diag`)

정직 브랜치 마이너 150계정 중 90개(60.0%)가 혼합 log10E ≥ 2를 넘었다(이론 한계 1%). 같은 관측열을 조건만 바꿔 다시 쌓아 원인을 갈랐다(`Diag.java`):

| 재생 조건(브랜치 마이닝, log10E ≥ 2 비율) | 값 |
| --- | --- |
| A. 판정이 나온 순서 + 그 시각의 p0 (엔진과 같다) | 60.0% |
| B. 미끼 관측 순서만 무작위로 섞음 | 0.0% |
| C. p0를 그 계정 자기 위약률×2로 바꿈(계정별 이질성 제거, 사후 오라클) | 64.7% |
| D. B와 C를 함께 | 3.4% |
| E. 판정이 나온 순서 대신 **자리가 생긴 순서** | 0.7% |

- **원인은 관측이 쌓이는 순서가 결과에 의존한다는 것.** 반응(HIT)은 창 안에서 일찍 나오고 무반응(MISS)은 창(240초)이 끝나야 나온다. 나온 순서대로 쌓으면 같은 시기 자리들의 반응이 무반응보다 먼저 들어가 E가 일시적으로 부풀고, "한 번이라도 문턱을 넘음"(ever)이 그 꼭대기를 잡는다. 곱셈 인자 하나하나는 귀무에서 평균 ≤ 1이어도 순서가 결과로 정해지면 부분곱은 상위마팅게일이 아니라서 Ville이 성립하지 않는다.
- **아닌 것**: 미끼·위약 배치 비대칭(미끼 반응률 1.13% = 위약 1.13%, 쌍 284/284), 혼합 사전분포(B에서 0%), 계정별 반응률 차이(C가 거의 안 바뀌고, 반응률 > p0인 계정이 37%여도 평균 비율은 약 0.9). 미끼가 진짜 광맥 분포를 흉내 내서 정직한 사용자가 지나가는 효과는 위약도 같은 분포라 대칭이므로 e-value를 키우지 못한다. 단, 시뮬레이터의 브랜치 에이전트는 광석을 쫓아가지 않아서 "보이는 광석으로 가다 지나감"은 실서버 `simtest honest-branch`로만 볼 수 있다.

### 수정

`AnchorCore`가 HIT·MISS·LATE_HIT 판정을 바로 증거 엔진에 넣지 않고 대기열에 둔다. `AnchorCore.expire(tick)`(플러그인은 1초마다, 시뮬레이터는 엔진 틱마다)이 창이 끝난 판정을 **(창 끝 틱, 쌍 번호, 나온 순서)** 순으로 내보낸다. 창 끝 틱 = 자리 생성 틱 + 창이라 결과와 무관하고(재생 E와 같은 순서), 한 쌍 안에서는 실제 반응 순서가 유지돼 "먼저 반응한 쪽" 검정은 그대로다. `EvidenceEngine`·`ResponseTracker`의 판정 로직은 건드리지 않았다(`Outcome`에 창 끝 틱 `due`만 추가). 반응이 증거에 반영되는 시점이 최대 창 길이(기본 240초)만큼 늦어지고, 그 사이 `/anchor status`에는 안 보인다. 종료 때는 `releaseAll()`로 남은 것을 저장한다. 대조군: 시뮬레이터 `--no-hold`(수정 전 동작), 코드의 `AnchorCore.holdUntilWindowEnd`.

**보장의 범위**: 순서가 결과와 무관해졌으므로, 자리마다 반응 확률이 (그때까지의 자리를 조건으로) p₀ 이하이면 혼합 E는 귀무에서 상위마팅게일이다. 자리 사이의 상관(같은 터널을 지나며 여럿에 반응)이 없다는 가정은 여전히 필요하고 이것은 증명이 아니라 시뮬레이터로 확인한 것이다(재생 E 0.7%, 수정 후 정직 혼합 ≥ 2는 0%). 생성 순서에서 반응이 이어질 확률은 따로 재지 않았다. 정확한 보장은 여전히 쌍 정확·먼저 반응 검정이 준다. 그래서 BOTH 규칙은 그대로 둔다. 테스트: `EvidenceOrderTest`(귀무에서 창 끝 순서 초과 확률 0.13% ≤ 1%, 나온 순서 3.8%, 대기·순서·초기화·종료 배선).

### 수정 전/후(같은 설정: `--runs 100 --honest 300 --minutes 120 --seed 1 --ppc 2`)

정직 300계정(동굴 150 + 브랜치 150, 각 최대 60분). 두 실행은 같은 관측을 쓴다(미끼 335/57976, 위약 338/57976 동일). 순서만 다르다.

| 동굴 혼합 log10E ≥ 1 / ≥ 2 | 26.7% / 3.3% | 0.0% / 0.0% |

**해석**: 이전의 "BOTH 94%, 8.7분"은 대부분 이 순서 부풀림이었다. 미끼 반응률은 2.5%, p₀는 0.7%라서 120분 동안 미끼 관측 약 470개로는 순서를 바로잡은 혼합이 10⁹(≈ 20.7 nats)에 거의 못 간다(관측당 증거 약 0.014 nats). 정직 오탐(혼합 ≥ 2: 60% → 0%)과 신뢰 낮은 엑스레이의 "확정"(신뢰20% 5%, 사실상 정직)도 같은 원인이라 같이 사라졌다. 이 설정에서 확정을 실제로 이끄는 것은 정확 검정인 "먼저 반응"(100%, 29분)이다. 기본 규칙 BOTH를 그대로 두면 엑스레이 검출이 8%로 떨어지므로, 확정 규칙을 `PAIRED`(먼저 반응만, 문턱 1/alpha)로 바꾸거나 혼합 문턱 alpha를 낮추는 것은 별도 결정이 필요하다(`confirm-rule`, `alpha`).

### 실서버: `/anchor simtest <플레이어> honest-branch <본갱도 블록수>`

사람 같은 정직 가지치기를 재현한다(권한 `anchor.admin`, 서바이벌만, 최대 본갱도 90블록). **미끼·위약 정보는 전혀 안 쓴다.** 서버 월드의 실제 블록만 읽는다.
- 본갱도를 보고 있는 가로 축 방향으로 파고, **3블록마다** 좌우를 번갈아 곁가지 12블록을 파고 되돌아온다(2칸 높이, 한 걸음 1블록, 4틱 간격).
- 매 걸음 반경(수평 6, 수직 ±4) 안에서 **공기에 닿은 진짜 다이아 광석**이 있으면(맨해튼 거리 8 이내, 이미 시도한 것은 제외) 그쪽으로 파 가서 캐고 정확히 원래 자리로 돌아와 경로를 이어 간다. 미끼는 클라이언트에만 있어 서버 월드에 보이지 않는다.
- 끝나면 "캔 진짜 광석 N개"와 2초 뒤 `/anchor status` 요약을 출력한다. 반응이 증거에 반영되는 것은 창 끝 이후라(수정 때문에) 요약 직후 `/anchor status`에는 아직 안 보일 수 있다. 창(240초)이 지난 뒤 다시 확인한다.
- 테스트: `SimRouteTest`(가지 간격·좌우 교대·한 걸음 1블록·광석 선택·왕복 복귀·자리 정보 미사용).
